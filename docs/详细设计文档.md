## 一、总体架构

### 1.1 系统组成

```

└────────┬────────┘   └────────┬────────┘   └────────┬────────┘

         └──────────┬──────────┴─────────────────────┘
                    │
            ┌───────▼────────┐
            │   Nginx        │  反向代理 + 静态资源 + SSL
            └───────┬────────┘
                    │
            ┌───────▼────────┐
            │ Spring Boot    │  REST API (单体)
```

### 1.2 模块划分(后端)

| 前缀 | 用途 | 鉴权 |

## 四、核心业务流程设计

### 4.1 登录与自动注册

```
小程序 wx.login() → loginCode
POST /api/public/wx/login {loginCode}
  后端: code2session → openid,未绑定手机号时签发短期 registrationToken
小程序 button[getPhoneNumber] → phoneCode
POST /api/public/wx/phone {phoneCode, registrationToken}
  后端:凭 phoneCode 调微信手机号接口 → phone
  若 phone 不存在 → 自动注册 member(staff_role=customer)
  若 openid 与已有手机号账号尚未绑定 → 在事务内绑定并校验唯一性
  签发正式 member token (含 memberId/staffRole/type=member), 缓存 Redis
返回 { token, member:{...脱敏} }
```

> `registrationToken` 仅用于完成注册,有效期 5 分钟且不能访问业务接口。手机号动态凭证只能使用一次;失败后由用户重新触发授权。服务端不向前端返回 openid、session_key 等敏感值。

### 4.2 会员身份码与权益卡核销码

**会员身份码(用户端)**:
- `GET /api/wx/member/code` 返回只含 `memberId` 签名标识的静态二维码 `lishuiwan://member-id?token=...`,不含手机号、openid 等明文信息。
- 身份码仅用于现场购卡、现金发卡和会员识别,不设置自动刷新,不可提交到核销接口。

**权益卡动态码(用户端)**:
- 用户从权益卡列表或详情进入核销码页,每 10s 调 `GET /api/wx/cards/{cardId}/code`。
- 后端校验卡归属、有效期和状态后生成 `{purpose=card_verify, memberId, cardId, exp, nonce}` + HMAC-SHA256 签名,缓存 Redis(key=`card-code:{nonce}`, TTL 90s)。
- 返回二维码字符串 `lishuiwan://card-code?token={base64url(payload)}.{signature}` 和 PNG 图片;页面隐藏时停止刷新。

**核销(管理端)**:
- 扫码得到内容 → `POST /api/wx/staff/card-codes/parse {token}` → 校验用途、签名、`exp`、Redis 状态、会员状态及卡状态 → 返回会员脱敏信息和二维码绑定的唯一权益卡。
- 核销员在扫码前输入本次人数/次数(默认 1),扫码后只选择该卡权益并确认 → `POST /api/wx/staff/verifications` `{requestNo, cardCodeToken, cardId, benefitId, quantity, operatorName}`。
- 服务端按 `requestNo` 判重,强制校验 token 中 `cardId` 与请求卡一致;开启数据库事务,插入 `t_consumed_member_code`、按 `version` 乐观更新权益且保证余额不小于扣减量,写核销记录,随后提交事务;提交后删除对应 Redis key。
- 事务提交后异步发送订阅消息;站内通知与核销记录在主事务内写入。任何校验或数据库步骤失败均不得扣减权益。

> `t_consumed_member_code` 主键、唯一索引 `uk_request_no`、数据库事务和权益卡 `version` 共同保证重复提交、进程异常及并发场景下不超扣。动态卡码仅在成功核销时消费;静态会员身份码可重复用于身份识别,现场发卡由 `requestNo` 保证幂等。两类码用途不同,后端禁止混用。

### 4.3 微信支付购卡(v1 模拟)

```
POST /api/wx/orders {productId, requestNo}
  校验商品上架 → 计算成交价 → 写订单与商品快照明细
  pay_status=0, expire_at=now+15min → 返回 orderNo
POST /api/wx/orders/{orderNo}/mock-pay {requestNo}      // 仅非生产环境启用
  Redis 锁 order:lock:{orderNo}
  校验状态=0且未过期 → 直接置 pay_status=1, paid_at=now
  paid_amount=payable_amount
  按 order_item 快照生成 membership_card(valid_from=now, valid_until=now+valid_days, benefits_remaining=total)
  卡状态 unused
  (预留: 真实支付时此步替换为统一下单+调起, 回调 /api/public/wx/pay/notify 校验签名后置已支付)
返回 {cardId}
```

> 订单置为已支付、生成权益卡必须由 `paySuccess(orderId)` 在同一数据库事务中完成,并以订单状态及 `membership_card.order_item_id` 唯一约束保证幂等。定时任务关闭超过 15 分钟的待支付订单。模拟支付由环境配置和后端权限双重限制,生产环境默认关闭。

### 4.4 现金发卡

```
管理端选择卡券类型 → 扫静态会员身份码 → `POST /api/wx/staff/member-codes/parse` 识别会员
输入启用状态的 Web 管理员密码进行二次授权
POST /api/wx/staff/cash-orders {requestNo, memberCodeToken, productId, paidAmount, adminPassword}
  校验 staff_role=admin、管理员密码、身份码签名与会员状态、paidAmount>0
  在同一事务内生成订单与快照明细(pay_method=cash, pay_status=1,
  payable_amount=当前成交价,paid_amount=实收,operator_member_id=当前登录会员 ID)
  生成 membership_card 归属该会员,写操作日志
  发"发卡成功"站内通知
返回 {orderId, cardId}
```

> `requestNo` 建唯一幂等记录/约束。`adminPassword` 仅用于本次服务端 BCrypt 校验,不写入幂等请求快照、操作日志或本地存储。任一启用状态的 Web 管理员密码均可完成授权。实收与应付不同时允许发卡,报表销售额按实收统计,差额可由订单明细追溯。

### 4.5 权益卡状态流转与过期

- 有限权益首次成功核销:`unused → using`;若全部有限权益的 remaining 为 0:`unused/using → used_up`。
- 查询和核销实时判断 `valid_until <= now` 并视为过期;定时任务(每 5min)扫描并固化 `expired` 状态,不能依赖定时任务保证拦截。
- 月卡(不限次类型)核销不扣 remaining,仅写记录,到 valid_until 自动过期。
- 任一权益为 `unlimited` 时,有效期内卡状态最高为 `using`,不会因其他有限权益耗尽而变为 `used_up`。

### 4.6 通知
- 站内通知:与核销/发卡在同一事务内写 `t_notification`,用户端 `GET /api/wx/notifications` 拉取。
- 订阅消息:用户主动操作时调用授权能力;核销事务提交后异步调用微信发送接口。失败不阻断主流程,记录失败原因并支持后台重试一次。

## 五、接口设计(核心)

> 统一响应:`{code:0, msg:"ok", data:{}}`;错误码:0 成功,40xxx 业务错误,50000 系统错误。
> 鉴权:Header `Authorization: Bearer <token>`。
> 所有业务写接口接收 `requestNo`(请求体或 `Idempotency-Key` Header),服务端按“调用方 + 接口 + requestNo”通过 `t_idempotency_record` 判重。分页参数统一为 `pageNo`(从 1 开始)、`pageSize`(默认 20,最大 100)。

### 5.4 关键业务错误码

| 错误码 | 含义 | 前端处理 |
|---|---|---|
| 40001 | 登录态无效/过期 | 清理 token 并重新登录 |
| 40301 | 角色权限不足 | 提示无权限并退出管理页面 |
| 40401 | 会员、商品、订单或卡不存在 | 提示数据不存在并刷新页面 |
| 40901 | requestNo 被不同参数复用,或原请求仍在处理中 | 停止提交并生成新的 requestNo;完全相同的已完成请求直接返回首次成功结果 |
| 40902 | 订单状态不允许当前操作 | 刷新订单状态 |
| 40903 | 并发更新冲突 | 拉取最新权益后提示重试 |
| 41001 | 会员码已过期或已使用 | 让顾客刷新会员码 |
| 42201 | 卡已过期/已用完 | 禁止核销并刷新卡列表 |
| 42202 | 权益不足或数量不符合步长 | 展示当前余额与允许步长 |

> HTTP 状态码与业务码同时使用;例如无权限返回 403,并在响应体携带 `40301`。服务端日志使用 traceId 关联,响应不得暴露堆栈和内部 SQL。

## 六、安全设计

1. **手机号**:仅后端解密;前端展示脱敏 `138****1234`;Web 端按权限展示完整号。
2. **二维码防伪与用途隔离**:静态会员身份码和动态权益卡核销码使用独立 `purpose` 及解析接口,禁止混用;动态核销码使用 HMAC-SHA256 签名 + 短时效 + nonce 服务端状态,成功核销时原子消费,防伪造与重放。日志不得记录完整 token。
3. **支付幂等**:请求幂等号 + 订单状态机 + 数据库唯一约束;订单锁仅用于削峰,回调/重复请求不重复发卡。
4. **核销并发**:数据库事务 + 乐观锁版本条件 + 幂等唯一索引保证不超扣;Redis 锁作为辅助优化。
5. **鉴权**:
   - 小程序 token 含 memberId + staffRole + `type=member`;`/api/wx/**` 校验会员,`/api/wx/staff/**` 进一步校验 staffRole。
   - Web token 独立签发且 claim 中 `type=admin`;`/api/admin/**` 只接受 Web admin token,不接受 member token。
   - `staffRole` claim 仅用于快速拒绝;服务端仍查询缓存/数据库中的当前角色。授权或取消授权后立即清理会员会话,防止旧 token 保留权限。
6. **限流**:登录、发码接口按 IP/会员限流(Redis 计数)。
7. **传输**:全链路 HTTPS(Nginx SSL);小程序强制 HTTPS。
8. **Web 跨域**:Nginx 同源部署(`/admin` 静态 + `/api` 代理)避免 CORS;或后端配置白名单 CORS。
9. **SQL 注入**:MyBatis-Plus 参数化;Web 端查询参数校验。
10. **密码**:Web 账号 BCrypt;不存明文。
11. **日志脱敏**:手机号、openid、token、微信凭证及支付敏感字段禁止明文写日志;操作日志保留 180 天。
12. **文件上传**:校验扩展名、MIME、文件头与大小,服务端生成文件名,上传目录禁止脚本执行。

## 十一、报表指标定义

| 指标 | 口径 |
|---|---|
| 销售额 | `sum(paid_amount)` where pay_status=1,按 pay_method 分微信/现金 |
| 售卡数量 | `count(order)` where pay_status=1 |
| 核销次数 | `count(verification)` |
| 新增会员 | `count(member)` by created_at 日期 |
| 卡类型占比 | 按 `order_item.product_snapshot.category` 聚合售卡数量,避免商品后续改分类影响历史口径 |
| 销售趋势 | 按 day 分组 `sum(paid_amount)` |
| 核销趋势 | 按 day 分组 `count(verification)` |

> 统计时间字段:销售使用 `paid_at`,核销使用 `verification.created_at`,新增会员使用 `member.created_at`;全部按 `Asia/Shanghai` 分桶。售卡数量当前等于已支付订单数(v1 每单一张),未来支持多件后应改为 `sum(order_item.quantity)`。退款未纳入 v1。

## 十四、关键测试清单
